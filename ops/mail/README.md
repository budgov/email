# 两个邮箱的生产发布

`production` 是独立的生产配置分支，也是仓库默认分支。`main` 可以继续同步上游，但同步不会自动发布邮箱。
Cloudflare 中两个 Worker 已断开旧 Git 构建连接（包含预览构建）；旧 `deploy-cloudflare.yml` 工作流已停用。
不要把上游强制同步到 `production`，不要重新启用旧发布流程。

## 更新邮箱

1. 将上游更新同步到 `main`，记录要发布的完整 40 位提交 SHA。
2. 打开 GitHub Actions → **Release production mail** → Run workflow，选择 `production` 分支。
3. 选择 `juuer-mail` 先升级，填写该 SHA；留空则发布 `ops/mail/source-revision` 中的已固定版本。
4. 等所有检查成功并确认业务正常，再用同一 SHA 发布 `budgov-mail`。
5. 验证完成后更新 `production` 上的 `ops/mail/source-revision`，记录新的默认版本。

应用源码从指定 SHA 单独取出；上游的 Wrangler 配置、发布工作流不会被用于生产发布。
`ops/mail` 中的适配代码每次都会重新加入两个 Worker，因此常规应用升级不会覆盖它。
部署工具固定为 Wrangler 4.90.0，兼容日期维持现有值，需要单独评估后升级。

## 保护和验证

- Worker 名、域名、数据库 ID 和 KV ID 固定在 `targets.json`。只允许发布两个现有实例。
- 发布前同时读取最新版本设置与实际运行版本；缺失的 db/kv 使用原有 ID 恢复，交叉绑定或未知资源会阻止发布。发布后两处必须同时完整，防止缺少绑定的预览版本造成设置页异常。
- 保留现有登录密钥、其他变量、可选 R2 与邮件发送限制；密钥不会写进仓库或生成配置。
- 先构建并检查 bundle，再发布；发布后核对线上资源 ID、实际数据库查询、KV 读取、前端资源及站点接口。
- 健康检查需要两分钟有效的专用 HMAC 签名，不返回邮件或用户内容，不发送邮件，不修改业务记录。
- 上游应用初始化包含数据库迁移。发布失败不会自动回滚数据库；必要时先评估迁移兼容性，再发布以前的应用 SHA。
- GitHub 权限和强制推送权限保持不变。人为覆盖 `production`、重新启用其他发布入口或上游不兼容的数据库迁移，仍需人工处理。

新版本增加绑定、MailHub 迁移或更改邮件处理入口时，先更新生产适配，再发布。不要用上游模板覆盖生产配置。
